## Machine note: the SSD is not reliable
`/Volumes/Toshiba` **unmounted spontaneously at 00:51 and remounted a minute later.** A `cd` into it failed, and a commit made seconds earlier was lost (its objects dangling, HEAD rolled back). Nothing else was damaged — every worktree, including 42 uncommitted WS-02 files, survived. Consequences for every session: push early (origin is the only durable copy); after any unexplained failure on that path, re-check `git log` against `origin` before assuming your work is there; keep expensive work-in-progress (a rewritten script, a long patch) in the session scratchpad on the internal disk. ADR-0021 put the working copy there for space; this is its cost. A second session lost a completed rebase the same way (git said "Successfully rebased"; the commit came back `not a valid object name` after the remount and the worktree was mid-rebase again, resolutions still on disk). Two follow-on rules from that: a `missing tree` from `git fsck` right after an operation can be **transient** — run `sync` and fsck again before calling it corruption; and **nobody runs `git gc` in the shared clone** while any worktree may still be missing work, because the dangling objects are the only remaining copy of it.

## Method note worth keeping: derive test fixtures from the geometry, never size them by eye
WS-05 reported that four tests failed on the first run of `FDFLaneWalker` and **three of the four were
the fixtures, not the code**: a walk budgeted its exact duration (600 frames for a 20 s walk measures
float error in 1/30, not the walker); a climb was compared against the flat crossing without its slant
(a 30 % grade walks 104.4 m per 100 m of ground — it is longer *and* slower, and only "slower" had been
modelled); and a detour budgeted the direct route's length, which is backwards, since being longer is
what makes a detour a detour. Their summary is the rule: *every fixture sized by eye was wrong; every
one derived from the geometry was right.* The budgets now carry that derivation in comments. Two build
cycles on an 8 GB Mac is roughly forty minutes of wall time, so this is a throughput note as much as a
correctness one — a fixture you cannot derive is a fixture you do not yet understand.

## The find of the night: a tag ini that never registered anything
WS-02's fix round ended by discovering that `Config/Tags/DF_Gameplay.ini` had **never registered a single
tag**. The 47 rows used `+GameplayTagList=` — correct in the `DefaultGameplayTags.ini` hierarchy, wrong
for a loose source under `Config/Tags/`, which `UGameplayTagsManager` reads with `LoadConfig` on that one
file (`GameplayTagsManager.cpp:582`) and which therefore wants the plain key. Consequence: every
`DF.SetByCaller.*` and every `GameplayCue.DF.*` leaf resolved to an invalid tag, `FireCue` returned early
on `!Cue.IsValid()`, and **no status or reaction cue had ever run** — while the unit tests stayed green,
because none of them asserted that the tags existed. The related halves: cue *family roots* are now
native module tags (an implicit parent of an ini leaf is not requestable), and `RegisterNativeCues()`
says why it did nothing instead of returning silently.

**`DF_Online.ini` (WS-11's, landed) had the identical bug and INT fixed it on main**, with the reason
written into the file so the next person appending a row does not restore it. The structural fix is
queued for WS-15: `DF.Unit.Tags.EveryIniTagRegisters`, which parses every `Config/Tags/DF_*.ini` and
asserts each tag resolves. The general lesson is worth more than the bug: **a subsystem that is
configured rather than called can be entirely absent while every test passes.** Anything that registers
itself — tags, cues, asset manager types, console commands, subsystem auto-instancing — deserves one
test that asserts the registration actually happened, because the failure mode is silence rather than
an error.

## RFC-0002: a contract that contradicted the sim it encodes
WS-02's review found `CONTRACTS/gas.md` stating the damage execution as `... → flat armor → vulnerability
→ shield`, where `Step.cs:2036-2053` does `... → vulnerability → shred front-arc leak ×1.35 → flat armor
floored at 0.5 → shield`. The code was right (it was ported from the sim); the **contract text** was
wrong, and had been since the P1 freeze. It is landed as RFC-0002 with no code change.

The order is load-bearing and the difference is not small: **10 damage on a marked (×1.25) Ram with
FlatArmor 2 is `max(0.5, 10 × 1.25 − 2)` = 10.5, not `(10 − 2) × 1.25` = 10.0** — every armored hit
differs by `DamageTakenFactor × FlatArmor`. Anyone who sized a weapon or a tower against the written
contract rather than the code has a number to recheck; WS-03, WS-04, WS-05, WS-06, WS-07, WS-21 and
WS-25 all consume it.

The lesson generalises past this one paragraph. **A contract written from memory beside a frozen
reference implementation drifts from it silently, and no test can catch that, because tests test the
code.** Where a contract claims to encode a spec, it must cite the spec's file and line — `gas.md` now
does, and RFC-0002 says so as the rule. Also fixed there: the claim "the execution has no literals" was
false (three `constexpr` values are the live numbers); the text now names all three, and their
`balance.json` dials are queued for WS-27.

## "Patching the mechanism where the condition needed stating"
WS-05's phrase for the mistake it made three times in one sitting, and the most transferable thing
anyone wrote down tonight. Each time the symptom was a guard that was *true for the wrong reason*, and
each time the first fix patched the mechanism that produced the symptom instead of stating the
condition the code actually depended on:

- **"which wave?"** — `bWaveActive` was asked to mean "still the wave we are releasing", which it
  cannot, because it is equally true of the wave that replaced it. Stated properly: a monotonic
  `WaveGeneration` captured once and compared.
- **"is this object alive?"** — an `EndPlay` override clearing `bWaveActive` looked sufficient, since
  every guard already asked that flag. It is not: **`EndPlay` never runs for an actor that never began
  play**, which is every automation world without a game state and is reachable in production during a
  teardown before BeginPlay dispatches. Stated properly: `IsLiveWave() = IsValid(this) && bWaveActive`,
  asked by every guard — both halves load-bearing, neither implying the other, and `EndPlay` demoted to
  tidy-up.
- **"what does this object say about itself?"** — `IsWaveActive()` still returned the raw flag, so a
  destroyed director told DFMatch and the mutables that a wave was running. The accessor answers
  `IsLiveWave()` too.

The shape is identical three times, one level further out each time. It is worth stating as a rule:
**when a guard is true for two different reasons, adding a fourth boolean is patching the mechanism —
name the condition and make every reader ask it.** Both of the wrong fixes were caught by the author's
own new test rather than by review, on a machine with 1.4 GB free, which is how they knew it was a
defect and not the flakiness.

Worth noting how the defect was found at all, because no single step would have: INT's reviewer raised
it, INT refuted it as unreachable *and flagged it forward anyway* because WS-19 and WS-24 will be
exactly the callers that make it reachable; the author wrote a test for the hazard rather than the bug;
the test then falsified their fix twice. The failure mode throughout was silence — a wave clearing out
of a torn-down match, never a crash.

## WS-02's falsification pass is the bar for a fix round
WS-02 closed its four findings and then did something no other round has: **reverted the four behaviour
lines in the working tree, rebuilt, re-ran, and recorded exactly what went red** — 5 tests (the 4 new
ones plus the extended one), with **no pre-existing test moving**. That second half is the part that
matters. It proves the new tests catch *these* bugs rather than catching collateral, and it is the only
evidence that separates a real regression test from one that passes for its own reasons — the failure
mode this programme has hit four times tonight, at four different levels. It cost one extra build.
Every fix round should end this way: revert your own fix, watch the named tests go red, restore.

Also worth recording, because it is a behaviour change nobody will see in an API diff: **F1 makes burns
and reaction bursts weaker than this branch previously produced.** A DoT tick no longer inherits the
applier's `UDFCombatSet.DamageFactor`, because the sim applies build factors at the weapon call site
(`Step.cs:558`) and none inside `Damage()`. WS-16's Overclock feed and WS-07's faction passives write
that attribute, so their DoTs quietly stop being amplified — correctly. If a designer later wants an
Overclocked hero's burn to tick harder, that is a **new rule with a new dial**, not a bug report;
`bAppliesSourceFactors` is the single place it changes.
