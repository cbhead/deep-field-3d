## Open questions
- **Join-code lobby visibility (C14).** EOS `INVITEONLY` lobbies cannot be found by a search, so a code-holder cannot reach the lobby by code alone. Implemented: the lobby is created `InvitationOnly`; `JoinByCode` runs `FindLobbies(DFJoinCode == code)` — on EOS that search only sees `PublicAdvertised` lobbies, so the host must flip the policy to `PublicAdvertised` while a code is live (`ModifyLobbyJoinPolicy`, one call, not yet wired — needs the EOS product to test). The code is unguessable (32^6) and rotates per approval and every 10 min; a stranger who reaches the lobby is only a *member*, never a player, until `ApproveJoin` (PreLogin refuses `notInvited`). Alternative for L2: keep INVITEONLY and carry the code through a friend invite. Decision wanted from INT/design before G2.
- **`DF.Message.JoinRequest` payload.** `FDFMsg_Player` has no field for the requester's online id (only `PlayerId` = seat, `Name`); the facade puts the display name in `Name` and exposes the id through `OnJoinRequest(const FDFOnlineId&, Name)` / `GetPendingJoinRequests()`. Proposed contract-append to C15: `FString OnlineId` on `FDFMsg_Player` (default empty), so UI can approve by id from the message alone.
- **Level curve ownership.** `IDFProgressionProvider::LevelFor` uses `1 + floor(Xp / xpPerLevel)` (balance dial `xpPerLevel`, default 100, cap 20) as a placeholder; WS-07 owns the real curve and should replace `UDFLocalProgressionProvider::LevelForXp`.
- ~~**`IDFSanctionsCheck` / `IDFAntiCheatCheck` seams** (C14) are not declared yet~~ — **declared 2026-09-26** in `DFCore/Public/Online/DFJoinSeams.h` beside `IDFJoinValidator` (ruling R3), and asked by `ADFGameMode::PreLogin`; pass-through at L1.
- **`UDFMatchSave` payloads** are skeletons with TODOs naming WS-04 (structures), WS-06/WS-03 (loadouts), DFMatch/WS-02 (match state), WS-09/WS-24 (mutables); the resume flow (`HostMigrationOffered` → `SaveResumed`) lands with the two-machine test once EOS exists.

## Spike verdict (ADR-0003 gate; OSSv2 on the UE 5.8.2 launcher build, Mac)
**Verdict: OSSv2 stays. No reason to fall back to OSSv1 was found.** Everything Level 1 needs ships in the launcher build with `Mac` and `Win64` in each plugin's `PlatformAllowList`, and all of it is already enabled in `DeepField.uproject`:
- **SDK**: EOS SDK 1.19.1 (`Engine/Source/ThirdParty/EOSSDK/SDK/Include/eos_version.h`), `Engine/Binaries/ThirdParty/EOSSDK/Mac/libEOSSDK-Mac-Shipping.dylib` present; `EOSShared` reads `[EOSSDK.Platform.<Name>]` (ids + secret) and `[EOSSDK] DefaultPlatformConfigName`.
- **Auth** (`OnlineServicesEOS`, `AuthEOS.cpp`): `IAuth::Login` with `LoginCredentialsType` `Auto` (reads `-AUTH_TYPE/-AUTH_LOGIN/-AUTH_PASSWORD`, the EGS exchange code), `ExchangeCode`, `Developer` (Dev Auth Tool `host:port` + credential), `PersistentAuth`, `AccountPortal`; `[OnlineServices.EOS.Auth] DefaultScopes`, `bAutoLinkAccount`; EAS (friends/presence/overlay) on top of Connect. Identity is the EOS `ProductUserId` behind `FAccountId`; `FOnlineIdRegistryRegistry` round-trips it to the string the facade stores in `FDFOnlineId`.
- **Lobbies** (`OnlineServicesEOSGS`, `LobbiesEOSGS.cpp`): `CreateLobby` (`EOS_LPL_INVITEONLY` for `InvitationOnly`, bucket `<product>:<build id>`), `FindLobbies` with schema-attribute filters, `JoinLobby`, `LeaveLobby`, `InviteLobbyMember`, `KickLobbyMember`, `ModifyLobbyAttributes`, `ModifyLobbyJoinPolicy`, and the events the facade binds (member joined/left, leader changed, attributes changed, invitation added, UI join requested). Lobby attributes are mapped onto `LobbyServiceAttribute1..N` from the plugin's `Config/Engine.ini`; the `DFLobby` schema fits (5 base search keys + `SchemaCompatibilityId`, 2 derived, 1 member).
- **P2P** (`SocketSubsystemEOS`): `NetDriverEOS` + `SocketEOS`; `[SocketSubsystemEOS] RelayControl=NoRelays|AllowRelays|ForceRelays` (C14 says `ForceRelays`); `IOnlineServices::GetResolvedConnectString` on an EOSGS lobby returns `[EOS:<host ProductUserId>]`, which the driver turns into a P2P socket; a URL that is not `EOS:` (or carries `?bIsLanMatch` / `?bUseIPSockets`) passes through to the Ip socket subsystem, so `smoke-listen.sh` keeps working after the switch.
- **Remote config**: `ITitleFile` (`TitleFileEOSGS.cpp`) for `GetRemoteConfig` at L2; `PlayerSanctionsEOSGS.cpp` exists for the `IDFSanctionsCheck` seam.
- **Null provider** (what the tests run on): Auth pre-registers every platform user as logged in (`OSSV2-<host>-<login id>`), so `Login(Auto)` adopts it; lobbies ride the LAN beacon (`FindLobbies` = LAN search, join policy forced `PublicAdvertised`, `MaxMembers` 100, schema not enforced, `Kick`/`Invite`/`ModifyLobbyAttributes` `NotImplemented`, host address in the `ConnectAddress` attribute). The facade tolerates each of those and `DF.Online.NullLogin` / `NullSession` prove login → lobby → join code → approval → handshake → leave headless.
- **Constraint found and solved**: `Searchable` attributes may only exist in the base schema, and the base is the hard-coded `LobbyBase` — hence the ini recipe above (was a schema-registry error that failed `NullLogin`).
- **Not proven yet (needs the portal product; the credential-time checklist)**: EOS login on this machine, an EOSGS lobby, and two machines over the relay. Checklist: (1) portal product / Dev sandbox / deployment / Game Client credential, application with `BasicProfile FriendsList Presence`; (2) INT applies `unreal/PLAN/rfcs/needs-int-eos-config.md` (ids, `DefaultServices=Epic`, `NetDriverEOS` definition, `RelayControl=ForceRelays`; secret via the gitignored platform ini); (3) Dev Auth Tool running, `-DFDevAuth=localhost:8081/<cred>` → `Login(Developer)` succeeds, identity is a `ProductUserId`; (4) host `CreateInviteOnlySession` → EOSGS lobby with the `DFLobby` attributes; (5) `JoinByCode` from the second machine — decide the INVITEONLY-vs-searchable question below (flip to `PublicAdvertised` while a code is live, or carry the code through an invite); (6) `ApproveJoin` → `LaunchMatch` (`?listen`) → client `JoinSession` → `NetDriverEOS` connects through `[EOS:<puid>]` with relays forced, `PreLogin` handshake passes; (7) join-in-progress at 150 ms emulation, `DF.Net.JoinLeaveRejoin`, `ResumeUnderNewHost`. If (6) fails on the relay in a way that is not configuration, the fallback is OSSv1 `OnlineSubsystemEOS` (present in the same engine) inside the same facade: only `IDFSessionBackend` and the lobby plumbing in `UDFOnlineSubsystem.cpp` would change; C13/C14 and everything above them would not.
- **Known gaps on Mac**: the EOS overlay is Windows-only, so `AccountPortal` opens a browser; the exchange-code path only exists under the EGS launcher (Dev Auth Tool covers development).

Proposed ADR (appended to `DECISIONS.md` as Proposed; INT numbers it): **OSSv2 spike verdict — keep `OnlineServicesEOS` behind `UDFOnlineSubsystem`**. Context: ADR-0003's spike gate. Decision: OSSv2 (`OnlineServicesEOS` + `OnlineServicesEOSGS` + `SocketSubsystemEOS`) is the provider behind the facade; the Null services are the headless test provider; the EOS switch is config only (needs-INT RFC); the lobby search keys live on `LobbyBase`. Consequences: no OSSv1 code in the project; the two-machine relay test is the remaining gate and runs the moment credentials exist; a relay failure would be absorbed inside `IDFSessionBackend` / the lobby plumbing, not above the facade.
